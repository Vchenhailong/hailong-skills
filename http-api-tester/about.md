# HTTP API测试技能

## 概述

这是一个专注于**基于场景的测试**（其中调用链往往包含多个场景，一个场景指的是具体请求与响应的一条业务逻辑分支；一个场景即一条用例）的综合性技能框架。它既不是单元测试，也不是孤立的HTTP接口测试，而是通过API调用链测试完整的业务工作流。该技能能够自动匹配语言栈成熟的测试框架，生成高质量报告。

## 何时使用

**必须在以下情况调用此技能：**

- 用户请求HTTP端点/API接口测试
- 用户需要分析API调用链和依赖关系
- 用户想要测试RESTful API或HTTP服务
- 用户需要跨API调用的参数依赖追踪
- 用户需要为API测试中的第三方服务设置Mock
- 用户询问API测试覆盖统计和报告
- 用户需要增强测试报告与JSON/Markdown/Web格式
- 用户需要基于场景的测试分析和可视化
- 用户需要交互式测试报告与搜索/过滤功能

**不要在以下情况调用：**

- 内部函数或类的单元测试
- 数据库直接访问测试
- 前端组件测试
- 性能/负载测试（使用performance-expert代替）

**优先级语言检测：**
此技能在调用时会自动检测项目的编程语言栈，优先检测后端语言用于API测试。

**检测方法：**

- ✅ **特征文件分析**：检查语言特定的配置文件
  - `pyproject.toml` 或 `requirements.txt` → Python
  - `pom.xml` 或 `build.gradle` → Java
  - `package.json` → Node.js
  - `go.mod` → Go
  - `Cargo.toml` → Rust

- ✅ **后端语言优先**：优先检测后端语言用于API测试

**语言检测结果的应用：**

- **自动框架选择**：自动选择相应的测试框架（pytest/TestNG/Jest/testing/cargo test）
- **自动依赖设置**：自动配置语言特定的依赖
- **自动报告元数据**：自动填充报告中的 `language_stack` 字段

**支持的语言栈：**

- Python (pytest)
- Java (TestNG)

## 测试场景定义（MANDATORY）

**关键：理解什么是测试场景**

**定义：**

- **测试场景指的是具体请求与响应的一条业务逻辑分支**，不是单个HTTP端点
- 场景代表调用链中的特定业务逻辑路径
- 每个场景是具有定义输入和预期输出的特定测试用例
- **一个调用链往往包含多个场景**
- **一个场景即一条测试用例**

**场景示例：**

```
调用链：用户注册流程
├── POST /auth/send-verify-code (发送验证码)
├── POST /auth/register (使用验证码注册)
├── POST /auth/token (登录获取令牌)
└── GET /auth/me (获取用户信息)

该调用链中的场景：
├── 场景1：成功注册用户（所有API调用成功）
├── 场景2：验证码无效注册（注册API返回错误）
├── 场景3：验证码过期注册（注册API返回错误）
└── 场景4：用户名重复注册（注册API返回错误）
```

**关键区别：**

- ❌ **场景 ≠ 单个HTTP端点**（例如：POST /auth/register 不是场景）
- ❌ **场景 ≠ 完整调用链**（例如：上述完整的用户注册流程是调用链，不是单个场景）
- ✅ **场景 = 特定业务逻辑分支**（例如：成功注册、验证码无效、验证码过期是不同的场景）
- ✅ **一个调用链往往包含多个场景**
- ✅ **一个场景即一条测试用例**
- ✅ **每个场景代表具有定义输入和预期输出的特定请求响应路径**

**为什么这个定义很重要：**

1. **测试覆盖率**：确保测试完整的业务工作流，而不仅仅是单个端点
2. **参数依赖**：捕获相关API调用之间的数据流
3. **业务逻辑**：验证端到端的业务流程
4. **集成测试**：测试端点如何作为一个系统协同工作

**场景与端点对比：**
| 方面 | 端点 | 调用链 | 场景 |
| -------- | ------------------- | -------------------------- | -------------------------------- |
| 范围 | 单个API操作 | 完整业务工作流（多个端点） | 调用链中的特定业务逻辑分支 |
| 示例 | POST /auth/register | 用户注册流程（4个端点） | 成功注册、验证码无效、验证码过期 |
| 测试类型 | 单元级集成 | 端到端集成 | 特定请求响应路径 |
| 依赖关系 | 无 | 调用之间的参数依赖 | 定义的输入和预期输出 |
| 关系 | 调用链的构建块 | 包含多个场景 | 一个场景即一条测试用例 |

**强制要求：**

- 测试设计必须基于场景（特定业务逻辑分支），而不是单个端点
- 调用链分析中识别的每个场景都必须有相应的测试用例
- 测试维度（正向业务场景、错误、边界情况、安全）应用于每个场景
- **关键要求**：正向业务场景必须被覆盖（不仅仅是快乐路径，而是所有正常的业务逻辑分支）
- **重要原则**：场景数一般是接口端点数的4-7倍，当小于该比例时，必须反复检查是否有未覆盖的场景，完善所有场景，直到确定所有场景都被覆盖了。

## 核心功能

### 1. 调用链分析

**自动HTTP调用关系分析：**

- 识别并记录API调用执行顺序
- 生成调用链关系图，使用Graph或Mermaid语法
- 展示静态调用链，包含参数传递可视化

**实现要求：**

- 实现调用链追踪器类
- 记录调用顺序
- 提取请求参数
- 捕获响应数据
- 生成调用链可视化的Mermaid语法

**输出格式：**

- Mermaid图表示例
- ASCII艺术树结构
- 参数传递可视化

### 2. 参数依赖解析

**解析参数依赖：**

- 识别上游请求返回值被用作下游请求输入的情况
- 跨API调用追踪数据流
- 文档化参数转换规则

**示例场景：**

- 上游：POST /api/auth/login 返回 {"token": "abc123", "user_id": 1001}
- 下游：GET /api/users/{user_id} 需要user_id从上游
- 依赖：user_id从登录响应 → users端点的user_id参数

**实现模式：**

- 实现参数依赖解析器类
- 分析调用链中的参数依赖
- 提取上游响应值
- 映射到下游请求参数
- 生成参数流文档

### 3. 业务值追踪

**追踪关键业务值：**

- 监控业务键的创建、传输和转换
- 跨API调用追踪数据生命周期
- 验证整个流程中的数据完整性

**示例业务键：**

- 订单ID
- 交易ID
- 用户会话令牌
- 支付引用

**实现：**

- 实现业务值追踪器类
- 记录值创建
- 记录值转换
- 报告值生命周期

### 4. 响应体验证

**关键参数和值验证：**

- 验证响应体关键参数和值（不仅仅是HTTP状态码）
- 深度验证嵌套JSON结构
- 通过响应数据验证业务逻辑正确性
- 支持灵活的断言策略（精确匹配、包含、正则等）

**实现要求：**

- 实现响应验证器类
- 验证响应结构和值
- 断言响应中的特定键值对
- 支持多种断言类型
- 验证嵌套JSON结构

**支持的断言类型：**

- `exact`：精确值匹配
- `contains`：值包含预期字符串
- `regex`：值匹配正则表达式模式
- `greater_than`：数值大于预期值
- `less_than`：数值小于预期值
- `not_null`：值不为None或空
- `type_check`：值匹配预期数据类型

**断言最佳实践：**

- 始终验证关键业务字段（ID、时间戳、状态）
- 验证数据类型和格式（邮箱、电话、日期）
- 检查错误场景中的预期错误消息
- 验证列表端点的分页元数据
- 验证计算字段（总计、平均值、计数）

### 5. 并发HTTP客户端

**关键：线程内顺序请求，跨线程并发**

**强制约束：**

- **单个线程内**：HTTP请求必须是顺序的（阻塞/同步）
  - 由于请求之间的数据依赖和调用依赖
  - 每个请求必须在下一个开始之前完成
  - 启用适当的参数传递和调用链追踪

- **跨多个线程**：HTTP请求是并发的（异步）
  - 不同线程同时执行独立请求
  - 线程之间没有数据依赖
  - 用于性能测试和负载测试

**为什么这个约束：**

1. **数据依赖**：API调用通常依赖于先前调用的数据（例如，登录 → 获取用户ID → 创建订单）
2. **调用依赖**：某些端点需要来自先前调用的认证令牌或其他值
3. **调用链完整性**：顺序执行确保准确的调用链追踪
4. **线程安全**：每个线程维护其独立的调用链
5. **性能**：并发线程模拟多个用户/客户端访问系统

**多线程和协程支持：**

- 支持多线程和基于协程的HTTP调用
- 默认为多线程方法
- 使用线程栅栏/屏障控制并发线程数
- 线程安全的调用链追踪和依赖追踪

**线程栅栏配置：**

- 使用`max_workers`参数控制最大并发线程
- 使用`Barrier`在特定点同步线程
- 确保线程安全的调用链追踪
- 支持同步和异步执行模式

**并发最佳实践：**

- 根据服务器容量设置适当的`max_workers`
- 使用线程栅栏避免压垮服务器
- 为并发请求实现适当的错误处理
- 确保线程安全的调用链追踪和依赖追踪
- 监控资源使用并相应调整并发
- 每个线程应该有其自己的独立调用链
- 验证线程内请求确实是顺序的
- 验证跨线程请求确实是并发的

### 6. 静态分析探针

**静态分析探针功能：**

### 8. 智能测试报告（会话统一生成）

**基于优先级的统一报告生成：**

- **会话结束后统一生成**：所有报告仅在完整测试会话结束后统一生成
- **完整数据收集**：从整个会话收集测试数据，确保报告完整性
- **首先检测外部报告工具运行时环境**：会话完成后检测可用工具
- 如果外部报告工具可用：使用语言特定的外部工具生成丰富的交互式统一报告
- 如果外部报告工具不可用：回退到框架默认HTML报告生成统一会话报告
- **多格式统一支持**：同时生成JSON、Markdown、Web格式的统一会话报告

**外部报告工具集成（优先）：**

- **Python**：allure-pytest、pytest-cov
- **Java**：Allure TestNG、JaCoCo
- **Node.js**：allure-jest、istanbul/nyc
- **Go**：Allure Go、go tool cover
- **Rust**：Allure Rust、tarpaulin/cargo-tarpaulin

**交互式报告功能：**

- 测试执行时间线
- 详细的测试步骤和附件
- 截图和日志集成
- 测试历史和趋势
- 环境信息
- 类别和严重性级别
- 测试持续时间统计

**回退HTML报告：**

- 简单、自包含的HTML报告
- 人类可读的格式
- 测试结果汇总

**报告检测逻辑（非阻塞）：**

- 检查外部报告工具是否已安装（非阻塞）
- 如果外部报告工具命令行工具可用则返回True
- 使用非阻塞模式生成外部报告
- 自动回退到HTML报告如果外部报告工具失败或不可用

**非阻塞外部进程集成最佳实践：**

## 基于模板的报告生成

### 架构概览

报告生成使用**基于模板的方法**，将数据与展示分离：

1. **模板（纯前端）**：
   - 单个HTML文件，包含嵌入式CSS和JavaScript
   - 语言无关 - 适用于任何后端
   - 通过浏览器fetch API动态加载JSON数据
   - 无需服务器端处理
   - 模板文件：report.html（基础模板）、report_enhanced.html（增强模板）
   - **强制性**：模板文件和资产目录必须复制到报告目录

2. **数据（JSON格式）**：
   - 由JSON Schema定义的标准JSON结构
   - 由语言特定的测试框架生成
   - 包含所有测试结果、调用链、覆盖率统计
   - 语言无关格式
   - Schema文件：report_data_schema.json

3. **资产（支持文件）**：
   - 包含CSS、JavaScript库（D3.js）、图片、字体
   - 模板正确渲染和可视化所必需
   - **强制性**：资产目录必须与模板文件一起复制到报告目录

4. **适配器（可选）**：
   - 提供生成标准JSON的便捷函数
   - 将框架特定格式转换为标准JSON
   - 自动填充元数据（时间戳、语言栈版本）
   - 根据JSON Schema验证数据
   - 适配器文件：python_adapter.py、java_adapter.java、nodejs_adapter.js、go_adapter.go

### 模板使用

**重要：模板和资产复制要求**

**强制性**：模板文件（report.html 或 report_enhanced.html）和资产目录必须在报告生成前复制到报告目录。这是基于模板的报告系统正常工作的关键要求。

**选项1：直接JSON加载（推荐）**

### JSON数据结构要求

**必填字段：**

- `report_metadata`：报告元数据（作者、AI模型、语言栈、时间戳（格式：YYYY-MM-DD HH:MM:SS）、统计）
  - `total_analyzed_scenarios`：分析出的总场景数（从调用链分析得出，一个调用链往往包含多个场景）
  - `total_test_cases`：应执行的测试用例数（即总用例数）
  - `total_http_endpoint`：总接口数（端点数）
  - `passed_scenarios`：通过的场景数（场景中所有测试用例都通过）
  - `failed_scenarios`：失败的场景数（场景中任意测试用例失败）
  - `skipped_scenarios`：跳过的场景数（场景未执行）
  - `scenario_pass_rate`：场景通过率（=通过场景数/测试执行时发现的场景数×100%）
  - `passed`：通过的测试用例数
  - `failed`：失败的测试用例数
  - `skipped`：跳过的测试用例数（意味着测试执行未执行该用例，例如因为依赖失败或跳过）
  - `pass_rate`：通过率（=通过测试用例数/总测试用例数×100%）
  - `total_exc_tests`：实际执行的测试用例数 (= 通过的测试用例数 + 失败的测试用例数，不包含跳过的）
  - `total_exc_endpoint`：测试覆盖接口数（测试执行所覆盖到的端点数）
  - `test_results`：包含详细信息的测试结果数组（每个测试用例的详细信息，包括请求参数、响应参数、断言详情等）
  - `call_chains`：API调用链可视化数组（每个场景的API调用链可视化数组）
  - `coverage_stats`：覆盖率统计（端点覆盖率=端点覆盖数/总端点数×100%；场景覆盖率=场景覆盖数/分析出的总场景数×100%）
  - `scenarios`：基于场景的测试分组

**完整Schema：**
请参阅 `report_data_schema.json` 获取完整的JSON Schema定义，包含所有字段类型和约束。

   - 说明: 一个调用链往往包含多个场景，因此场景数通常大于调用链数
   - 示例（EXAMPLE）：


## API端点关系分析（MANDATORY）

**关键：在编写测试用例之前分析API端点关系**

在实现任何测试用例之前，必须：

1. 分析API端点关系和依赖
2. 识别参数依赖关系
3. 生成调用链图
4. 输出关系文档
5. 然后基于此分析设计测试用例

**为什么采用此方法：**

- 确保端点交互的全面测试覆盖
- 防止遗漏关键集成场景
- 早期识别潜在的数据流问题
- 提供系统行为的清晰文档
- 使测试设计更加系统和彻底

**分析工作流：**

### 步骤1：端点发现和文档

**要求：**

- 发现并记录所有可用的端点
- 按资源组织端点
- 记录端点描述、请求体、响应体

### 步骤2：依赖分析

**要求：**

- 分析端点之间的依赖关系
- 识别参数映射
- 记录上游到下游的依赖

### 步骤3：调用链生成

**要求：**

- 为不同业务场景生成调用链
- 记录每个步骤的详细信息
- 包含参数提取和依赖

### 步骤4：Mermaid图生成

**要求：**

- 生成调用链的可视化表示
- 使用Mermaid语法
- 包含参数传递信息

### 步骤5：关系文档输出

**要求：**

- 生成全面的关系文档
- 包含端点清单
- 包含依赖分析
- 包含调用链
- 包含Mermaid图

**强制输出文件命名（在测试框架标准分析目录下）：**

- `call_chain_analysis.md`：完整的调用链分析文档，包含端点关系
- `dependency_analysis.md`：端点之间的参数依赖分析
- `call_chain_diagram.md`：调用链可视化的Mermaid图

**各语言栈默认分析目录：**

- **Python (pytest)**：`tests/analysis/`
- **Java (TestNG)**：`src/test/analysis/`
- **Node.js (Jest)**：`tests/analysis/` 或 `__tests__/analysis/`
- **Go (testing)**：`tests/analysis/` 或与测试文件同目录
- **Rust (cargo test)**：`tests/analysis/` 或 `src/analysis/`

### 步骤6：测试用例设计

**要求：**

- 基于分析设计测试用例
- 包含成功路径测试
- 包含错误场景测试（包括HTTP状态码和业务返回码，如果适用）
- 包含边界值测试

### 步骤7：覆盖率差距检测和自检（MANDATORY）

**关键：检测和报告覆盖率差距**

在生成测试用例定义后，必须执行自检以识别调用链分析和测试用例设计之间的任何覆盖率差距。

**为什么这个步骤：**

- 确保全面测试覆盖
- 防止遗漏关键集成场景
- 识别未测试的端点和依赖
- 提供可操作的建议用于测试用例补充
- 验证测试设计的完整性

**差距检测维度：**

1. **最长依赖链覆盖**（CRITICAL）：存在依赖关系的最长链
   - ✅ 最大依赖链的完整覆盖情况
   - ✅ 最大依赖链中每个节点的功能覆盖
   - ✅ 最大依赖链中节点间的依赖关系验证
   - ✅ 最大依赖链中的数据一致性验证
2. **业务流程覆盖率**：
   - 调用链覆盖率：所有调用链是否有相应测试
   - 场景覆盖率：所有业务场景是否被覆盖
   - 数据一致性覆盖：完整流程中的数据一致性验证
   - 各链节点的参数验证覆盖
   - 各链节点的错误处理覆盖
   - 各链节点的业务返回码覆盖（没有返回码时，响应体结构需要覆盖）
3. **通用覆盖率**：
   - 依赖覆盖率：所有参数映射是否被测试
   - 错误场景覆盖率：所有端点的错误案例（包括HTTP状态码和业务返回码，如果适用）
   - 边界值覆盖率：边界值和边界案例测试
   - 安全场景覆盖率：认证和授权测试

**差距严重性级别：**

- **CRITICAL**：
  - ✅ 未测试的最大依赖链（存在依赖关系的最长链）
  - ✅ 最大依赖链中的关键节点（POST/DELETE）
  - ✅ 未测试的调用链、关键端点（POST/DELETE）
- **HIGH**：未测试的具有高业务影响的端点、错误场景、安全场景
- **MEDIUM**：未测试的依赖、边界案例、边界值
- **LOW**：未测试的可选功能或次要场景

**检测到差距时的强制操作：**

1. **审查差距报告**：仔细审查覆盖率差距报告
2. **优先级差距**：首先解决CRITICAL和HIGH严重性差距
3. **补充测试用例**：为识别的差距创建测试用例
4. **重新运行分析**：补充后，重新运行差距检测以验证覆盖率
5. **更新文档**：更新测试用例定义和文档
6. **阻塞要求**：在继续测试执行之前，必须解决CRITICAL和HIGH差距

## 测试用例设计框架

**PREREQUISITE: 测试用例调用路径必须明确基于调用链分析结果。**

**强制要求：场景覆盖匹配**

- HTTP场景测试用例必须基于调用链分析的场景进行设计
- **关键：调用链分析提供框架（要测试哪些端点和场景）**
- **关键：测试维度（边界案例、错误场景、安全场景）应用于每个调用链场景**
- 如果场景测试用例少于调用链分析结果，必须继续实现以匹配
- 在补充缺失场景的同时，必须维护所有现有测试用例

**应用于每个调用链场景的测试维度：**
对于调用链分析中识别的每个场景，必须覆盖：

1. 正向业务场景（成功的场景）
2. 错误情况（HTTP状态码和业务返回码，如果适用）
3. 边界情况（边界值、空输入）
4. 安全场景（身份验证、授权）
5. 数据验证场景

**关系：**

- 调用链分析 = 框架（测试什么 - 端点和场景）
- 测试维度 = 覆盖率（如何测试 - 边界案例、错误、安全）
- 两者是互补的，不是互斥的

**测试用例设计原则：**

- ✅ 采用"原子层+业务层"分层设计模式，但是原子层不能作为测试用例，而是由业务层组织并调用
- ✅ 必须以系统中识别的最大依赖链作为核心测试设计依据
- ✅ 基于调用链分析设计完整业务流程测试，包括先后对每个调用链节点的参数验证和错误处理
- ✅ 测试用例调用路径遵循API端点关系分析中识别的调用链
- ✅ 每个调用链从分析中必须有相应的测试用例
- ✅ 最大依赖链的测试覆盖率必须达到100%
- ✅ 测试用例必须验证分析中识别的参数依赖
- ✅ 测试执行顺序：先正常主流程，后其他业务分支流程，最后各链节点的异常流程
- ✅ 测试执行顺序遵循分析中定义的调用序列

**测试用例元数据要求：**

- **测试标题**：必须具有描述性，清楚说明正在测试什么
- **测试描述**：必须说明测试目的、测试数据和预期行为
- **测试标题和描述必须在HTML报告表头中显示所有测试**
- **文件名**：测试用例文件名（非被测对象的文件名）必须被捕获并包含在报告中
- **类方法名**：测试方法标识符必须被捕获并包含在报告中
- **输入参数**：发送到API端点的请求参数必须被记录
- **输出参数**：从API端点接收的响应参数必须被记录
- **断言信息**：测试用例中的每个断言步骤必须记录在"断言信息"（Assertion Info）表头列中
  - **关键：断言绝不能仅限于HTTP状态码**
  - **关键：断言必须验证响应体中的关键信息**（例如：特定字段值、业务返回码、信息描述）
  - **例外**：如果响应体为空或不包含这些字段，HTTP状态码断言是可接受的
  - 断言详情包括：断言类型、期望值、实际值、断言结果
  - 通过的断言以正常字体颜色显示
  - 失败的断言以红色字体显示，便于识别
  - 断言信息必须在主报告表格中可见，不能在测试用例详情中
- **元数据必须被捕获并包含在生成的报告中**

**测试数据命名约定：**

- ✅ 前缀测试数据为`AIT_`（例如：`AIT_test_user_001`）
- ✅ 使用UUID或时间戳以实现唯一性
- ✅ 测试后清理测试数据
- ✅ 使用Fixture机制管理测试数据的生成和清理
- ✅ 测试数据统一管理，支持Session级共享

**非固化数据禁止硬编码要求：**

- ❌ **禁止**：在测试代码或报告中硬编码非静态数据
- ✅ **推荐**：使用配置文件、环境变量或数据生成函数获取动态数据
- ✅ **推荐**：将测试数据存储在单独的文件中
- ✅ **推荐**：使用自定义参数化模式处理多组测试数据
- ❌ **不推荐**：使用测试框架提供的参数化模式（如 pytest 的 @pytest.mark.parametrize）
- ✅ **推荐**：在运行时生成唯一数据（如时间戳、UUID）
- ✅ **推荐**：从API响应或数据库中读取动态标识符，而不是硬编码

**关键：测试文件必须组织以支持统一会话执行**

   - ✅ `testcases/`：测试用例目录，按业务模块/场景组织
   - ✅ `testcases/atomic/`：原子层目录，存放单个API端点测试

3. **测试组织策略**：使用框架特定的组织机制：

   - ✅ 测试文件按**核心业务模块+业务流程**原则组织
   - ✅ 核心业务模块由业务发起目的、最终产出物、业务领域归属确定

- 测试文件必须在测试执行开始前组织好
- 如果未建立统一执行能力，不能继续执行测试
- 这是生成完整会话报告的前提条件

## 测试执行工作流

### 阶段1：测试发现

- 扫描遵循框架约定的测试文件
- 识别测试用例和fixtures
- 构建测试执行计划

### 阶段2：测试执行

- 按依赖顺序执行测试
- 捕获调用链和依赖
- 记录测试结果和指标

### 阶段3：结果验证

- 验证响应状态码和业务返回码（如果适用）
- 验证响应模式
- 检查业务逻辑正确性

### 阶段4：报告生成（会话结束后统一生成）

- **统一报告生成时机**：所有测试执行报告仅在**完整测试会话结束后**统一生成
- **会话完成要求**：报告生成必须等待会话中的所有测试用例执行完成后才开始
- **综合数据收集**：从整个测试会话收集执行结果、覆盖率统计、调用链和断言信息
- **单一报告生成**：生成包含完整会话结果的统一报告，而非单个测试报告
- **一次会话一份完整数据文件**：每次测试会话生成且仅生成一份完整的数据文件，包含该会话所有测试结果，不生成多份分散的数据文件
- **全量数据文件**：生成的数据文件必须包含该会话的所有测试结果（成功、失败、跳过），不是部分数据文件
- **非增量更新**：每次测试会话都重新生成完整的数据文件，不是在旧文件基础上添加新数据
- **外部工具检查**：会话结束后检查外部报告工具可用性（Allure、覆盖率工具等）
  - 如果可用：使用语言特定的外部工具生成统一会话报告
    - Python: allure-pytest、pytest-cov
    - Java: Allure TestNG、JaCoCo
    - Node.js: allure-jest、istanbul/nyc
    - Go: Allure Go、go tool cover
    - Rust: Allure Rust、tarpaulin/cargo-tarpaulin
  - 如果不可用：使用语言特定的HTML报告器生成统一HTML报告
    - Python: pytest-html
    - Java: JUnit HTML或ExtentReports
    - Node.js: Jest HTML Reporter或Mochawesome
    - Go: gotestsum with HTML output
    - Rust: cargo2junit with HTML转换
- **会话级覆盖统计**：基于所有已执行测试计算整体会话覆盖率
- **失败测试汇总**：编译和识别会话中所有失败的测试和问题
- **报告合并整合**：将多个测试文件/场景的结果合并到统一会话报告中
- **非阻塞执行**：所有外部进程在非阻塞后台模式运行，但只在会话结束后启动
- **控制台摘要输出**：会话完成后生成统一的控制台摘要输出

**技术实现考虑：**
以下要求（调用链、断言信息、文件名等）被定义为测试报告的质量标准。然而，实际实现取决于所选报告工具的能力。当标准报告工具（Allure、pytest-html、Jest HTML Reporter等）无法完全满足这些要求时，应考虑以下方法：

1. **自定义报告生成器开发**：为每个语言栈开发自定义报告生成器，以确保完全符合所有要求
2. **后处理增强**：使用标准报告工具生成基础报告，然后应用后处理脚本添加自定义内容
3. **需求适配**：调整特定显示要求以匹配可用报告工具的能力，同时保持信息完整性

**优先方法**：建议开发自定义报告生成器以完全符合所有报告要求。

### 阶段5：报告验证（MANDATORY）

- 验证报告完整性和正确性
- 验证所有必需的报告元素都存在
- 确保调用链以表头列形式显示
- 检查测试元数据完整性

**报告验证要求：**
这是确保测试报告在交付前符合所有质量标准的强制性最终步骤。

**验证检查项：**

1. **表头信息验证**
   - ✅ 测试标题显示在报告表头中
   - ✅ 测试描述显示在报告表头中
   - ✅ 文件名（测试用例文件名，非被测对象的文件名）包含在报告中
   - ✅ 类方法名包含在报告中
   - ✅ 调用链以独立的表头列显示（不在测试用例详情中）
   - ✅ 断言信息以独立的表头列"断言信息"（Assertion Info）显示
   - ✅ 失败的断言以红色字体显示，便于识别

2. **调用链验证**
   - ✅ 每个测试在"调用链"（Call Chain）表头列中显示相应的调用链
   - ✅ 调用链图正确显示端点关系
   - ✅ 参数依赖在调用链中清晰标注
   - ✅ 调用链在主报告表格中可见，不在测试用例详情中

3. **断言信息验证**
   - ✅ 测试用例中的每个断言步骤记录在"断言信息"（Assertion Info）表头列中
   - ✅ 断言详情包括：断言类型、期望值、实际值、断言结果
   - ✅ 通过的断言以正常字体颜色显示
   - ✅ 失败的断言以红色字体显示，便于识别
   - ✅ 断言信息在主报告表格中可见，不在测试用例详情中

4. **出入参数验证**
   - ✅ 请求参数记录在报告中
   - ✅ 响应参数记录在报告中
   - ✅ 参数传递关系清晰记录
   - ✅ 参数值显示在报告中

5. **元数据验证**
   - ✅ 测试执行时间被记录
   - ✅ 测试状态正确显示
   - ✅ 断言结果详细且准确
   - ✅ 所有必需的元数据被捕获并包含
   - ✅ 文件名指测试用例文件名，非被测对象的文件名
   - ✅ 断言信息格式正确，失败的断言以红色显示

**验证结果处理：**

- **PASS**：报告符合所有要求，可以正常输出
- **WARNING**：部分信息缺失但仍可输出（记录警告信息）
- **FAIL**：关键信息缺失，需要补充或修复后重新生成报告
  - **关键：FAIL的用户通知**：当验证失败时，必须明确告知用户：
    - 详细的失败原因和哪些验证项失败
    - 具体的缺失或错误信息
    - **提示自动修复**：明确告知用户可以请求自动修复验证失败
  - 用户可以审查失败信息并决定是否请求自动修复

**阻塞要求：**

- 具有CRITICAL或HIGH严重性验证失败的报告不能交付
- 必须修复验证问题并重新生成报告后才能继续
- 必须告知用户阻塞性质，用户可以请求自动修复

## 测试约束（STRICT）

### 1. 测试数据命名约定（MANDATORY）

**REQUIRED Test Data Prefix:**

- **非真实世界数据验证测试数据** MUST使用前缀 "AIT*" 或 "ait*"
- 这适用于：用户名、产品名、测试业务逻辑数据等
- **不包括**：应用自维护的id、uuid（如id、uuid等应该只从响应体读取，或在必要时通过查询相应数据从数据库获取）
- **真实世界数据验证测试数据** 不需要前缀

**区分标准：**

**需要AIT\_前缀**：用于测试业务逻辑、创建测试对象、mock数据

- 示例：`AIT_test_user_001`、`AIT_order_12345`、`AIT_test_product_xyz`
- 字段类型：username、name、product_name、title、description等

**不需要AIT\_前缀**：用于验证真实世界数据格式

- 示例：`test@example.com`（验证邮箱格式）、`13800138000`（验证电话格式）、`110101199001011234`（验证身份证格式）
- 字段类型：email、phone、phone_no、phone_number、mobile_no、mobile_number、Tel、Telephone、id_card、id_number、social_security、ssn等（不区分大小写）

**应用自维护字段处理：**

- **id、uuid等字段**：只从响应体读取，或在必要时通过查询相应数据从数据库获取
- **date、time、datetime、timestamp等字段**：应用自维护
  - 如果写入：根据类型规则生成
  - 如果读取：只从响应体读取，或在必要时通过查询相应数据从数据库获取

**未提及字段的兜底策略：**

对于测试数据字段未在`REAL_WORLD_DATA_FIELDS`和`SELF_MAINTAINED_FIELDS`列表中提及的情况，应用以下兜底策略：

**规则优先级：**

1. **REAL_WORLD_DATA_FIELDS**（最高优先级）
2. **SELF_MAINTAINED_FIELDS**（中等优先级）
3. **兜底策略**（最低优先级）

**兜底策略：**

- **对于未提及字段**：应用自维护
  - **如果写入**：根据业务类型从字段名推断获取值
    - 类型相关字段（type、enum、status、state等）：使用业务特定值
    - 用户相关字段（user、customer、client等）：使用`AIT_{field}_001`
    - 订单相关字段（order、transaction、payment等）：使用`AIT_{field}_001`
    - 产品相关字段（product、item、goods等）：使用`AIT_{field}_001`
    - 地址相关字段（address、location、region等）：使用`AIT_{field}_001`
    - 默认：使用`AIT_{field}_001`
  - **如果读取**：只从响应体读取，或在必要时通过查询相应数据从数据库获取

此兜底策略适用于所有语言栈：

- **Python (pytest)**：在`TestDataValidator`类中实现
- **Java (TestNG)**：在`TestDataValidator`类中实现
- **Node.js (Jest)**：在`TestDataValidator`类中实现
- **Go (testing)**：在`TestDataValidator`函数中实现
- **Rust (cargo test)**：在`TestDataValidator`结构体中实现

### 2. 测试数据上下文获取（MANDATORY）

**FORBIDDEN:**

- 手动构造测试对象依赖
- Mock测试对象依赖
- 创建假数据用于测试对象关系

**REQUIRED:**

- 测试对象依赖必须从API上下文获取
- 使用实际API响应来获取依赖数据
- 遵循实际数据流通过系统

**示例：**

**错误：手动构造依赖**

- 手动设置user_id
- 手动设置token
- 手动构造订单数据

**正确：从API上下文获取依赖**

- 通过API创建用户，获取user_id
- 通过API登录，获取token
- 使用API响应的数据创建订单

**实现：**

- 实现依赖上下文管理器
- 从API上下文存储值
- 从API上下文获取值
- 确保依赖只能从API获取

**允许的环境：**

- development、dev、test、staging、local

**禁止的环境：**

- production、prod、live

### 4. 无直接内部访问

**FORBIDDEN:**

- 直接访问内部实现以进行测试操作
- 调用私有方法或内部函数
- 绕过API层测试内部组件

**REQUIRED:**

- 所有测试操作必须通过HTTP端点进行
- 将系统视为黑盒
- 仅通过API响应验证

### 5. 测试执行约束（MANDATORY）

**STRICTLY FORBIDDEN:**

- 绕过HTTP请求层进行测试操作
- 直接调用服务层方法
- 直接操作数据库表
- 执行SQL语句或其他低级操作

**REQUIRED:**

- 所有测试操作必须通过HTTP端点进行
- 将系统视为黑盒
- 仅通过API响应验证
- 遵循适当的异常处理工作流

**异常处理工作流：**

当测试中遇到异常时，遵循此流程：

**a) 业务代码审查：**

1. 全面审查业务代码
2. 检查功能缺陷或逻辑错误
3. 验证业务规则和约束
4. 验证数据流和转换

**b) 详细诊断信息：**
提供全面的诊断信息，包括：

- 异常堆栈跟踪
- 失败点的关键变量值
- 执行路径分析
- 请求/响应数据
- 环境状态

**c) 业务代码修复：**

1. 基于诊断结果，如果需要则修复业务代码
2. 验证修复不会破坏现有功能
3. 确保修复符合业务需求
4. 记录更改和推理

**d) 测试代码调整：**

1. 仅当异常源自测试代码时调整测试代码
2. 常见测试代码问题：
   - 测试数据构造错误
   - 测试逻辑缺陷
   - 不正确的断言
   - 缺失设置/清理
3. 优化测试代码而不改变业务逻辑

### 6. 数据库操作标准（MANDATORY）

**允许：**

- 查询业务数据库表结构在测试环境中
- 检索元数据信息：
  - 数据类型定义
  - 字段约束
  - 表关系
  - 索引信息

**STRICTLY FORBIDDEN:**

- 使用查询的数据库表信息来执行写操作
- 直接执行INSERT、UPDATE、DELETE操作在数据库
- 通过数据库查询修改测试数据
- 绕过API层进行数据操作

**REQUIRED:**

- 所有测试数据准备和维护必须通过：
  - 应用API端点
  - 指定的测试数据管理工具
- 所有数据验证必须通过API响应进行

**测试数据管理：**

- 通过API创建测试数据
- 通过API更新测试数据
- 通过API删除测试数据
- 通过API查询测试数据
