# HTTP API Tester 测试流程步骤文档

## 概述

本文档详细说明了 HTTP API 测试的完整流程，包括每个步骤的执行内容和关键输出信息。

---

## 步骤 1: 自动编程语言检测与环境自检（如果环境都已符合用户预期，即可跳过）

### 执行内容
- 检测项目编程语言栈
- 验证语言版本是否满足要求
- 检查所有必需的依赖包
- 验证命令行工具是否可用
- 提供自动安装功能

### 关键输出信息
- **检测到的语言栈**: Python/Java/Node.js/Go/Rust
- **语言版本**: 具体版本号（如 Python 3.11+）
- **测试框架**: 自动选择的框架（pytest/TestNG/Jest等）
- **依赖状态**:
  - ✅ 绿色: 已安装且可用
  - 🟡 橙色: 缺失但可自动安装
  - 🔴 红色: 必需但无法自动安装
- **平台信息**: Windows/Linux/macOS
- **安装建议**: 缺失依赖的安装命令

---

## 步骤 2: API 端点关系分析与静态分析探针（测试设计前必须执行）

### 执行内容
- 分析 API 端点之间的关系和依赖
- 识别端点之间的参数依赖
- 生成调用链图
- 输出关系文档
- 实现并运行静态分析探针
  - 扫描源代码中的 API 端点定义
  - 识别端点关系和依赖
  - 生成调用链分析数据
  - 验证调用链完整性
  - 检测潜在的依赖问题
  - 输出标准化分析结果
  - **泛化实现**: 使用泛化方法而非硬编码进行参数依赖分析
  - **状态感知分析**: 考虑数据状态、业务状态和多角色间数据交换等依赖
- 执行多角色分析
  - 识别系统中所有业务角色（如用户、管理员、客服等）
  - 为每个角色创建端点映射表，明确标记每个端点的角色归属
  - 分析完整的跨角色业务流程，覆盖从发起者到审批者再到通知接收者的全流程
  - 为每个跨角色业务流程创建专门的调用链分析
  - 识别跨角色操作之间的状态传递和依赖关系
  - 在静态分析探针中配置角色特定端点的识别规则（如 `/admin/` 前缀）
  - 在调用链图中明确标记不同角色的操作

### 测试场景定义（关键概念）

**测试场景的定义**:
- **测试场景指的是具体请求与响应的一条业务逻辑分支**，不是单个 HTTP 端点
- 场景代表调用链中的特定业务逻辑路径
- 每个场景是具有定义输入和预期输出的特定测试用例
- **一个调用链往往包含多个场景**
- **一个场景即一条测试用例**

**示例场景**:
```
调用链: 用户注册流程
├── POST /auth/send-verify-code (发送验证码)
├── POST /auth/register (使用验证码注册)
├── POST /auth/token (登录获取令牌)
└── GET /auth/me (获取用户信息)

该调用链中的场景:
├── 场景1: 成功注册用户（所有API调用成功）
├── 场景2: 验证码无效注册（注册API返回错误）
├── 场景3: 验证码过期注册（注册API返回错误）
└── 场景4: 用户名重复注册（注册API返回错误）
```

**关键区别**:
- ❌ **场景 ≠ 单个 HTTP 端点**（例如，POST /auth/register 不是场景）
- ❌ **场景 ≠ 完整调用链**（例如，上述完整的用户注册流程是调用链，不是单个场景）
- ✅ **场景 = 特定业务逻辑分支**（例如，成功注册、验证码无效、验证码过期是不同的场景）
- ✅ **一个调用链往往包含多个场景**
- ✅ **一个场景即一条测试用例**
- ✅ **每个场景代表具有定义输入和预期输出的特定请求响应路径**

**场景 vs 端点对比**:
| 方面     | 端点                | 调用链                     | 场景                             |
| -------- | ------------------- | -------------------------- | -------------------------------- |
| 范围     | 单个 API 操作       | 完整业务工作流（多个端点） | 调用链中的特定业务逻辑分支       |
| 示例     | POST /auth/register | 用户注册流程（4个端点）    | 成功注册、验证码无效、验证码过期 |
| 测试类型 | 单元级集成          | 端到端集成                 | 特定请求响应路径                 |
| 依赖     | 无                  | 调用之间的参数依赖         | 定义的输入和预期输出             |
| 关系     | 调用链的构建块      | 包含多个场景               | 一个场景即一条测试用例           |

### 关键输出信息
- **call_chain_analysis.md**: 完整的调用链分析文档（位于测试框架标准分析目录）
  - 所有发现的 API 端点列表
  - 端点之间的调用关系
  - 参数依赖关系
  - 识别的测试场景列表
  - **最大依赖链识别**: 系统中识别的最长依赖链（存在依赖关系的最长链）
  - **角色分析**: 系统中识别的所有业务角色及角色-端点映射
  - **跨角色调用链**: 跨越多个业务角色的完整业务流程调用链
- **dependency_analysis.md**: 参数依赖分析（位于测试框架标准分析目录）
  - 端点间参数映射关系
  - 数据流向说明
  - 角色间依赖关系矩阵
- **call_chain_diagram.md**: 调用链可视化图（位于测试框架标准分析目录）
  - Mermaid 格式的调用链图
  - 端点执行顺序
  - 参数传递路径
  - 最大依赖链的突出显示
  - 不同角色操作的明确标记
  - 跨角色业务流程的可视化
- **静态分析探针输出**:
  - **文件位置**: 项目根目录下的 `scripts/` 目录
  - **执行文件**: 根据语言栈命名（如 `call_chain_probe.py` 用于 Python）
  - **输出结果**:
    - 标准化的调用链分析数据
    - 调用链完整性验证报告
    - 潜在问题检测结果
    - 支持与其他分析工具集成
    - **角色覆盖报告**: 显示每个角色的端点覆盖情况
    - **角色-端点映射**: 明确标记每个端点的角色归属
    - **跨角色依赖分析**: 识别跨角色操作之间的依赖关系
    - **角色特定端点优先级**: 标记 CRITICAL 级别的角色特定端点

**各语言栈默认分析目录：**
- **Python (pytest)**：`tests/analysis/`
- **Java (TestNG)**：`src/test/analysis/`
- **Node.js (Jest)**：`tests/analysis/` 或 `__tests__/analysis/`
- **Go (testing)**：`tests/analysis/` 或与测试文件同目录
- **Rust (cargo test)**：`tests/analysis/` 或 `src/analysis/`

## 步骤 3: 测试场景定义与覆盖率检查

### 执行内容
- 基于调用链分析定义测试场景
- 每个场景代表调用链中的特定业务逻辑分支
- 应用测试维度到每个场景
- 执行覆盖率缺口检查（内部检查过程，不生成独立文件）
- 执行角色覆盖检查
  - 检查所有业务角色的端点是否都已分析
  - 检查跨角色业务流程是否完整
  - 检查 CRITICAL 级别的角色特定端点是否 100% 覆盖
  - 检查跨角色操作之间的状态传递和依赖关系是否已分析

### 关键输出信息
- **场景定义**:
  - 场景 ID 和名称
  - 场景描述
  - 包含的端点列表
  - 调用顺序
- **测试维度应用**:
  - 正常业务场景
  - 错误场景（HTTP状态码和业务返回码）
  - 边界情况
  - 安全场景
  - 数据验证场景
- **覆盖率缺口检查**（内部检查过程，不生成独立文件）:
  - **场景数量经验规则**: 场景数量通常是 API 端点数量的 4-7 倍，当小于该比例时，必须反复检查是否有未覆盖的场景，完善所有场景，直到确定所有场景都被覆盖了
  - **最长依赖链覆盖**（CRITICAL级别）: 存在依赖关系的最长链
    - 最大依赖链的完整覆盖情况
    - 最大依赖链中每个节点的功能覆盖
    - 最大依赖链中节点间的依赖关系验证
    - 最大依赖链中的数据一致性验证
  - **业务流程覆盖率**:
    - 调用链覆盖率检查
    - 场景覆盖率检查
    - 数据一致性覆盖
    - 各链节点的参数验证覆盖
    - 各链节点的错误处理覆盖
    - 各链节点的业务返回码覆盖（没有返回码时，响应体结构需要覆盖）
  - **通用覆盖率**:
    - 端点覆盖率检查
    - 依赖覆盖率检查
    - 错误场景覆盖率检查
    - 边界情况覆盖率检查
    - 安全场景覆盖率检查
- **缺口严重级别**:
  - CRITICAL:
    - 未测试的最大依赖链（存在依赖关系的最长链）
    - 最大依赖链中的关键节点（POST/DELETE）
    - 未测试的调用链、关键端点
  - HIGH: 高业务影响的未测试端点、错误场景、安全场景
  - MEDIUM: 未测试的依赖、边界情况
  - LOW: 未测试的可选功能

## 步骤 4: 测试用例设计

### 执行内容
- 采用"原子层+业务层"分层设计模式设计测试用例，但是原子层不能作为测试用例，而是由业务层组织并调用
- 原子层代码文件只是被调用的，而不是直接测试的
- 必须以系统中识别的最大依赖链作为核心测试设计依据
- 基于调用链分析结果设计完整业务流程测试，包括先后对每个调用链节点的参数验证和错误处理
- 确保每个调用链都有对应的测试用例
- 应用测试维度到每个场景
- 定义测试元数据
- 确定测试执行顺序：先正常主流程，后其他业务分支流程，最后各链节点的异常流程

### 关键输出信息
- **分层设计模式**:
  - **原子层**: 作为业务流程的组成单元，包含单个API端点的基础功能定义
    - 定义每个API端点的参数验证规则
    - 定义每个API端点的错误处理场景
    - 由业务层测试组织并调用，不单独作为测试用例执行
    - 原子层代码文件只是被调用的，而不是直接测试的
  - **业务层测试**:
    - 基于原子层，以最大依赖链为核心设计完整业务流程测试
    - 组织并调用原子层定义的API功能
    - 确保最大依赖链的测试覆盖率达到100%
    - 使用Session级共享数据，统一管理
- **测试执行顺序**:
  - 先执行正常主流程测试
  - 再执行其他业务分支流程测试
  - 最后执行各链节点的异常流程测试
- **测试用例定义**:
  - 测试标题: 描述性标题，明确测试内容
  - 测试描述: 测试目的、测试数据、预期行为
  - 文件名: 测试用例文件名（非被测对象文件名）
  - 类方法名: 测试方法标识符
  - 输入参数: 发送到 API 端点的请求参数
  - 输出参数: 从 API 端点接收的响应参数
  - 断言信息:
    - 断言类型
    - 预期值
    - 实际值
    - 断言结果
    - 失败断言以红色字体显示
  - 调用链: 完整的调用链路径
- **测试数据命名**:
  - 非真实世界数据验证: 使用前缀 "AIT_" 或 "ait_"
  - 真实世界数据验证: 不需要前缀
  - 应用自维护字段: 从响应体读取或数据库查询
  - 使用Fixture机制管理测试数据的生成和清理

## 步骤 5: 测试文件组织

### 执行内容
- 组织测试文件以支持统一会话执行
- 使用框架特定的组织机制
- 确保单个命令可执行所有测试

### 关键输出信息
- **目录结构**:
  - `testcases/`: 测试用例目录，按业务模块/场景组织
  - `testcases/atomic/`: 原子层目录，存放单个API端点测试
  - 必须为系统中识别的最大依赖链创建专门的测试文件
  - 最大依赖链测试文件命名：`test_max_dependency_chain.py`
- **核心业务模块原则**:
  - 测试文件按**核心业务模块+业务流程**原则组织
  - 核心业务模块由业务发起目的、最终产出物、业务领域归属确定
  - 多模块调用链以核心业务模块为主要命名依据
- **文件命名规则**:
  - 原子层：直接使用业务模块名称，如 `order.py`，存放单个API端点测试
  - 业务层：使用 `test_{core_module}.py` 格式，如 `test_order.py`，包含完整业务流程测试
- **测试文件结构**:
  - Python (pytest): 使用`pytest.ini`或`conftest.py`配置
  - Java (TestNG): 使用组或 testng.xml 配置
  - Node.js (Jest): 使用 describe 块或目录结构
  - Go (testing): 使用构建标签或包结构
  - Rust (cargo test): 使用模块组织或条件编译
- **执行命令**:
  - 运行所有测试的命令
  - 运行特定场景的命令
- **业务模块组织**: 按业务模块/场景组织测试文件

## 步骤 6: 测试执行

### 执行内容
- 执行测试发现
- 按依赖顺序执行测试
- 捕获调用链和依赖关系
- 记录测试结果和指标

### 关键输出信息
- **测试发现结果**:
  - 识别的测试用例列表
  - 识别的测试夹具
  - 测试执行计划
- **测试执行结果**:
  - 总测试数
  - 通过测试数
  - 失败测试数
  - 跳过测试数
  - 执行时间
- **调用链信息**:
  - API 调用执行顺序
  - 参数传递关系
  - 响应数据
- **并发执行指标**:
  - 使用的线程数
  - 执行时间

## 步骤 7: 报告生成（会话结束后统一生成）

### 执行内容
- 检测外部报告工具是否可用
- 生成 JSON 格式报告
- 生成 Markdown 格式报告
- 生成 Web 格式报告
- 复制模板和资源文件

### 关键输出信息
- **JSON 报告 (report.json)**:
  - report_metadata:
    - author: "hailong.chen"
    - ai_model: "GLM-4.7"
    - language_stack: 检测到的语言栈
    - test_framework: 使用的测试框架
    - generated_at: "YYYY-MM-DD HH:MM:SS"
    - total_analyzed_scenarios: 分析的场景总数
    - total_test_cases: 要执行的测试用例总数
    - total_http_endpoint: HTTP 端点总数
    - passed_scenarios: 通过的场景数
    - failed_scenarios: 失败的场景数
    - skipped_scenarios: 跳过的场景数
    - scenario_pass_rate: 场景通过率 (= 通过场景数 / (通过场景数 + 失败场景数 + 跳过场景数) × 100%)
    - passed: 通过的测试用例数
    - failed: 失败的测试用例数
    - skipped: 跳过的测试用例数
    - pass_rate: 通过率 (= 通过测试用例数 / 总测试用例数 × 100%)
    - total_exc_tests: 执行的测试用例数 (= 通过的测试用例数 + 失败的测试用例数，不包括跳过的测试用例)
    - total_exc_endpoint: 测试的端点数
    - total_execution_time: 总执行时间
    - project_name: 项目名称
  - test_results: 测试结果数组（每个测试用例的详细信息）
  - call_chains: API 调用链可视化数组
    - chain_id: 调用链 ID
    - chain_name: 调用链名称
    - endpoints: 端点列表
    - description: 描述
    - calls: 调用详细信息数组
      - method: HTTP 方法
      - endpoint: API 端点路径
      - status_code: HTTP 状态码
      - request_headers: 请求头对象
      - request_body: 请求体对象
      - response_headers: 响应头对象
      - response_body: 响应体对象
      - execution_time: 执行时间（秒）
  - coverage_stats: 覆盖率统计
    - endpoint_coverage: 端点覆盖率 (= 测试的端点数 / 端点总数 × 100%)
    - endpoints_covered: 测试的端点数
    - endpoints_total: 端点总数
    - scenario_coverage: 场景覆盖率 (= 测试的场景数 / 分析的场景总数 × 100%)
    - scenarios_covered: 测试的场景数
    - total_analyzed_scenarios: 分析的场景总数
    - call_chain_coverage: 调用链覆盖率 (= 测试的调用链数 / 调用链总数 × 100%)
    - call_chains_covered: 测试的调用链数
    - call_chains_total: 调用链总数
  - scenarios: 基于场景的测试分组
    - test_count: 场景中的测试用例数
    - passed_count: 通过的测试数
    - failed_count: 失败的测试数
    - tests: 测试结果数组

- **Markdown 报告 (report.md)**:
  - 测试文件路径
  - 调用链信息
  - 类方法详细信息
  - 输入/输出参数
  - 测试执行摘要
  - 覆盖率统计

- **Web 报告 (report.html 或 report_enhanced.html)**:
  - D3.js 交互式可视化
  - 搜索和过滤功能
  - 展开/折叠功能
  - 实际测试的 API 完整路径
  - 请求详情（方法、URL、头、体）
  - 响应详情（状态码、头、体）
  - 适当的样式、正确的交互、优雅的视觉设计、响应式布局

- **模板和资源文件**:
  - **模板文件**:
    - report.html: 基础模板文件
    - report_enhanced.html: 增强模板文件（推荐，包含更丰富的可视化功能）
    - 纯前端HTML文件，包含嵌入式CSS和JavaScript
    - 无需服务器端处理，通过浏览器fetch API动态加载JSON数据
    - 语言无关，适用于任何后端
  - **资源目录 (assets/)**:
    - 包含CSS样式文件
    - 包含JavaScript库（如D3.js用于可视化）
    - 包含必要的图片和字体资源
    - 用于模板的正确渲染和交互式可视化
  - **强制性要求**:
    - 模板文件和资源目录必须复制到报告目录
    - 资源目录必须与模板文件一起复制
    - 技能会自动完成模板和资源文件的复制工作

## 附录: 关键原则和约束

### 核心测试原则（必须执行）
1. **测试身份和测试目的**: 定义测试身份（谁执行测试）和测试目的（验证什么业务行为）
2. **检查响应体中的业务关键点**:
   - 断言必须验证响应体关键业务字段值或响应体的内容；无内容则根据实际返回结构做断言处理
   - 仅当响应体为空时才接受 HTTP 状态码断言

### 测试数据命名约定
- **非真实世界数据验证测试数据**必须使用前缀 "AIT_" 或 "ait_"
- 适用于: 用户名、产品名、测试业务逻辑数据等
- **不包括应用自维护的 id、uuid**（应从响应体读取，或在必要时从数据库查询）
- **真实世界数据验证测试数据**不需要前缀
- 适用于: 验证真实邮箱格式、真实手机号格式、真实身份证格式等

### 测试场景定义
- **测试场景指的是具体请求与响应的一条业务逻辑分支**，不是单个 HTTP 端点
- 场景代表调用链中的特定业务逻辑路径
- 每个场景是具有定义输入和预期输出的特定测试用例
- **一个调用链往往包含多个场景**
- **一个场景即一条测试用例**

### 自动回退策略
- 测试报告生成绝不能失败
- 如果主要报告生成方法失败，必须应用自动回退策略以确保始终生成报告
- **主要方法**: 基于模板的报告（report.html + report.json）
- **次要方法**: 框架特定的 HTML 报告器（pytest-html、Jest HTML Reporter 等）
- **第三方法**: 终端和终端输出与详细摘要

### 数据文件生成原则
- 每个会话一个完整数据文件
- 完整数据文件（包含会话的所有测试结果）
- 非增量更新（每次测试会话重新生成完整数据文件）

### 非阻塞外部进程
- 所有外部应用进程（报告生成、覆盖率工具等）在后台模式下运行
- 永不阻塞测试执行或应用进程
- 如果外部进程失败，自动回退到替代方法
- 报告生成仅在完整测试会话完成后进行
