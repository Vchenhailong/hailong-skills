API调用链静态分析探针 - AST + 图算法版本

================================================================================
探针设计文档
================================================================================

【核心设计】

1. 使用AST精确解析代码结构（替代正则表达式，避免硬编码模式匹配）
2. 构建依赖图（有向图，邻接表实现）
3. 使用图算法分析依赖关系和断点
4. 基于关键业务入口生成核心调用链（控制数量，避免路径爆炸）

【图模型】

- 节点：API端点（Endpoint）
- 边：依赖关系（Dependency），带类型和置信度
- 权重：依赖强度（0.0-1.0）

================================================================================
发现策略（Discovery Strategy）
================================================================================

1. 端点发现策略（示例）
   - 方法：AST解析路由装饰器
   - 目标：@router.get/post/put/delete/patch 装饰的异步函数
   - 提取信息：
     - HTTP方法（从装饰器函数名）
     - 路径（从装饰器参数）
     - 函数参数（包括类型注解）
     - 文档字符串
     - 认证信息（从参数名推断：current_user/current_admin等）

2. 依赖发现策略（示例）
   - 数据依赖：参数名以 \_id 结尾 → 查找对应的 POST 创建端点
   - 认证依赖：has_auth=True 的端点 → 链接到对应的登录端点
   - 层级依赖：RESTful路径层级 /resources → /resources/{id}
   - 状态依赖：路径包含 approve/reject/enable/disable 关键词

3. 关键入口发现策略（配置化示例）

```text
   以下端点被视为业务调用链的起点：
   - /auth/token (POST) - 用户认证入口
   - /auth/register (POST) - 用户注册入口
   - /admin/login (POST) - 管理员认证入口
   - /services (POST) - 服务发布入口
   - /service-requests/ (POST) - 服务需求发布入口
   - /payments/ (POST) - 支付创建入口

   说明：这些入口需要人工配置，因为业务入口是语义概念，无法从代码自动推断
```

================================================================================
去重策略（Deduplication Strategy）
================================================================================

问题：从入口点DFS遍历会产生大量路径组合（80万+），需要有效去重

策略：基于关键入口的最长路径生成（贪心算法）

1. 入口选择
   - 只从配置的关键业务入口生成调用链
   - 避免从所有入口点生成导致数量爆炸

2. 路径生成策略
   - 每个入口只生成一条链（最长路径）
   - 使用贪心算法：每次选择置信度最高的依赖
   - 限制最大深度（默认6层），防止无限延伸

3. 为什么不使用全路径遍历？
   - 全路径会产生指数级数量的链
   - 大多数路径是业务上无意义的组合
   - 最长路径通常代表主业务流程

4. 为什么不识别状态分支？
   - approve/reject 等状态分支需要业务语义理解
   - AST无法自动识别互斥操作
   - 需要运行时信息或人工标注

================================================================================
局限性说明
================================================================================

1. 不可避免的硬编码
   - 关键业务入口列表（需要领域知识）
   - 认证参数模式（示例如 current_user/current_admin等）
   - 状态关键词（示例如 approve/reject/enable/disable）

2. 无法自动识别的内容
   - 业务状态机（什么是状态？状态如何转换？）
   - 互斥操作（示例如 approve和reject是互斥的）
   - 业务规则（什么条件下可以审核？）

3. 设计权衡
   - 选择了"精准但需配置"而非"全自动但混乱"
   - 调用链数量 < 端点数量
   - 每条链都是可理解的核心业务流程
